#### API entry point (`cmd/api/main.go`)

- `main` turns SIGINT and SIGTERM into context cancellation and exits 1 on error. `run` does all
  the wiring, so every dependency is explicit and there is no global state.
- Start-up order: configuration → logger → database (5 s ping) → migrations → probes → listener →
  server. Any failure stops the process before it accepts traffic.
- The configuration is logged at start-up without the database URL.

#### Configuration (`internal/platform/config`)

- `Load` parses `DATABASE_URL` (required), `HTTP_ADDR` (default `:8080`), `LOG_LEVEL` (default
  `info`) and `LOG_FORMAT` (`json` or `text`, default `json`) with caarlos0/env. It reports every
  missing or invalid variable in one error.
- It reads only the variables passed in (`main` passes the process environment) and never a
  `.env` file, so tests never depend on the process environment.
- `Config` implements `slog.LogValuer`, which leaves the database URL out of logs.

#### HTTP server (`internal/platform/httpserver`)

- `NewRouter` returns a chi router with three middlewares, outermost first: request ID (reusing
  an incoming `X-Request-Id`), access log and panic recovery.
- The access log writes one line per request with `request_id`, `method`, `path`, `status`,
  `bytes` and `duration_ms`: 5xx at error level, successful health probes at debug level.
- Panic recovery logs the panic and its stack as structured JSON and answers 500. It runs inside
  the access log, so the failed request is still logged. `http.ErrAbortHandler` is re-panicked,
  as net/http expects.
- `Serve` applies server timeouts (header 5 s, read 15 s, write 30 s, idle 60 s). When its
  context is cancelled, it stops accepting connections and gives in-flight requests up to 10 s.
  Request contexts don't derive from the signal, so a shutdown never cancels them.

#### Health probes (`internal/platform/health`)

- `GET /healthz` always answers 200 and checks nothing, so a database outage never gets a
  healthy process restarted.
- `GET /readyz` runs every registered check (today, a PostgreSQL ping) under a 2 s timeout. It
  answers 200, or 503 with the state of each check, e.g.
  `{"status":"unavailable","checks":{"postgres":"unavailable"}}`. Error details are logged,
  never returned.
- A check is a plain `func(ctx) error`, so a new dependency is one more entry in `cmd/api`.

#### Database and migrations (`internal/platform/database`, `migrations/`)

- `Open` connects through GORM (pgx driver) with explicit pool limits (20 open and idle
  connections, 30 min lifetime, 5 min idle time), pings within 5 s and closes the pool if the
  ping fails.
- GORM logs through slog at warn level and above: errors and queries slower than 200 ms, as
  parameterised SQL, so bind values (personal data) never reach the logs. Database errors are
  translated, e.g. a unique violation becomes `gorm.ErrDuplicatedKey`.
- `Migrate` applies the embedded goose SQL migrations under a PostgreSQL advisory lock, so several
  instances can start at once, and logs each applied file and the resulting version.
- `00001_baseline.sql` is a deliberate no-op that starts version tracking; the first real tables
  arrive with the first business capability.

#### Web app (`frontend/src`)

- Vue 3.5, TypeScript 6 and Vite 8, scaffolded by create-vue with Vitest, ESLint, Oxlint and
  Prettier. No router, store or component library yet.
- `ApiStatus.vue` calls `/readyz` once when it mounts and shows "API: ready", "API: not ready"
  (503) or "API: unreachable" (any other status or a network error, including the development
  proxy's 502 when the API is down).
- `vite.config.ts` proxies `/api` and `/readyz` to `localhost:8080`, so the browser stays on one

#### Web server (`frontend/Dockerfile`, `frontend/nginx.conf`)

- nginx looks `api` up in Docker's DNS on each request, so it still reaches a recreated API

#### Containers (`Dockerfile`, `compose.yaml`, `.dockerignore`)

- The backend image builds every `./cmd/*` binary and runs on `alpine:3.24` as uid 10001. Later

### Phase 2A — Customer and Commerce domain design

#### Context

Phase 1 delivered the platform skeleton, with no business code. Phase 2A designs the
Customer and Commerce bounded contexts. Two things depend on them:

- the segmentation engine, a later phase, which will query this data to turn an LLM-generated
  rule into a recipient list;
- a seeder, which will fill it with several thousand synthetic customers.

This phase is design only, and nothing in the repository changes until you approve. The
design follows CLAUDE.md (capability packages, GORM kept out of the domain, schema changes
only through goose) and the Phase 1 decisions. Campaign, AI, Delivery and the segmentation
engine itself are out of scope.

#### The main challenge: these contexts are read models

Nothing in this system places orders or edits customers. The only writers are the seeder
and, from the delivery phase on, opt-outs such as an unsubscribe link or an SMS "STOP".
Every other access is a segment query that reads both contexts at once. Three consequences:

- **The schema gets most of the effort.** Every segment depends on its constraints and indexes.
- **The domain stays thin:** value objects plus three small aggregates whose constructors guard
  the invariants. Repositories, services and interfaces wait until a caller needs them; the
  seeder will be the first.
- **Unused parts of the initial model go.** If neither segmentation nor the seeder uses
  something, it is removed:

| Initial concept | Change | Reason |
|---|---|---|
| Basket entity and its Status | Removed; a basket is the customer's `basket_items` rows | Each customer has one open basket; "abandoned" is derived from `added_at` and later orders |
| BasketItem.UnitPrice | Removed | Prices don't change in this system; order lines record what was paid |
| Order.Status | Removed (decision 3) | There is no checkout, payment or fulfilment flow; an order is a completed purchase |
| Product.Description | Removed | Segments never filter on it; messages need only the name |
| Country | Removed if the market is Turkey only (decision 1) | With one country it is dead weight |
| Customer.UpdatedAt | Removed | Nothing updates customer rows; permissions keep their own timestamp |

Also left out on purpose: payments, shipping, addresses, stock, variants, discounts, returns,
category hierarchy, birth date and gender, a consent audit trail, and soft deletes.

#### 1. Bounded contexts

- **Customer** (`internal/customer`): who can be contacted, where, in which language and on
  which channels. Cities are reference data inside it.
- **Commerce** (`internal/commerce`): what customers buy or intend to buy: categories,
  products, baskets and orders.

How the contexts relate:

- Commerce refers to customers by ID only; Customer is upstream.
- The segmentation phase will read the tables of both contexts in single SQL statements.
  Joining in the database is what keeps a segment to one query instead of joining in memory.
  Customer and Commerce still own every write. I'll record this deliberate coupling in
  DECISIONS.md.
- The delivery phase will read contact points and permissions, and record opt-outs through
  the `customer` package.

#### 2. Aggregates, entities, value objects and invariants

##### Customer context

**Customer** is the aggregate root. It holds:

- ID, first name and last name;
- Email, and Phone (optional, see decision 2);
- city ID and preferred Language;
- created at, which is the signup date (the seeder backdates it);
- one Permission per Channel.

Its value objects:

| Value object | Rule |
|---|---|
| Email | Trimmed, lowercased and syntactically valid |
| Phone | E.164 format (`+905321234567`), which SMS providers expect |
| Language | A closed set of ISO 639-1 codes: `tr`, `en` |
| Channel | `sms` or `email` |
| Permission | Channel, granted, updated at |

Invariants:

1. First and last name are not empty.
2. A permission can only be granted for a channel the customer can be reached on: SMS needs a
   phone. Revoking is always allowed.
3. A missing permission means "not permitted". Commercial messages need prior opt-in under
   Turkish e-commerce law (consent is registered in İYS) and under GDPR.
4. Email and phone uniqueness spans all customers, so the database enforces it.

**City** is reference data: an ID and a name, seeded once and read-only. It is not an aggregate.

##### Commerce context

- **Category**: reference data, an ID and a unique name. Categories are flat, with no hierarchy.
- **Product**: a plain aggregate with an ID, a category, a name and a Price. The name is not
  empty and the price is above 0.
- **Basket**: the aggregate root, identified by its customer's ID. Each item has a product, a
  quantity and an added-at time. Invariants:
  - every quantity is above 0;
  - there is one line per product, so adding a product already in the basket raises its quantity.
- **Order**: the aggregate root, with an ID, a customer ID, an ordered-at time and lines. Each
  line is a value object: product, quantity, unit price. Invariants:
  - there is at least one line, and only one line per product;
  - quantities are above 0 and unit prices are 0 or more;
  - the order is immutable once created;
  - the total is the sum of quantity × unit price. It is computed, not stored, so nothing can
    drift out of sync.
- **Money**: int64 kuruş, in a single currency (TRY).

##### Rules for all domain types

- **No GORM.** Domain types carry no GORM tags; persistence maps them to unexported row structs
  in the same package.
- **Time is a parameter.** Operations receive the time as `at time.Time` and never call
  `time.Now()`. This keeps tests deterministic and lets the seeder write past activity.
- **Personal data is masked in logs.** Email and Phone implement `slog.LogValuer` and log
  masked values, so personal data cannot reach the logs by accident.

#### 3. Relational schema

This listing assumes the recommended options. "identity" means
`bigint GENERATED ALWAYS AS IDENTITY`, and every time column is `timestamptz`.

```text
cities
  id                  identity     PK
  name                text         NOT NULL UNIQUE                 'İstanbul'

customers
  id                  identity     PK
  first_name          text         NOT NULL
  last_name           text         NOT NULL
  email               text         NOT NULL UNIQUE                 lowercased by the domain
  phone               text         NULL UNIQUE, CHECK E.164
  city_id             bigint       NOT NULL FK cities
  preferred_language  text         NOT NULL CHECK IN ('tr','en')
  created_at          timestamptz  NOT NULL DEFAULT now()          signup date

notification_permissions               PK (customer_id, channel)
  customer_id         bigint       FK customers ON DELETE CASCADE
  channel             text         CHECK IN ('sms','email')
  granted             boolean      NOT NULL
  updated_at          timestamptz  NOT NULL

categories
  id                  identity     PK
  name                text         NOT NULL UNIQUE

products
  id                  identity     PK
  category_id         bigint       NOT NULL FK categories
  name                text         NOT NULL UNIQUE
  price_minor         bigint       NOT NULL CHECK > 0             kuruş

basket_items                           PK (customer_id, product_id)
  customer_id         bigint       FK customers ON DELETE CASCADE
  product_id          bigint       FK products
  quantity            integer      NOT NULL CHECK > 0
  added_at            timestamptz  NOT NULL

orders
  id                  identity     PK
  customer_id         bigint       NOT NULL FK customers
  ordered_at          timestamptz  NOT NULL

order_items                            PK (order_id, product_id)
  order_id            bigint       FK orders ON DELETE CASCADE
  product_id          bigint       FK products
  quantity            integer      NOT NULL CHECK > 0
  unit_price_minor    bigint       NOT NULL CHECK >= 0            price paid, kuruş
```

Relationships:

- a city has many customers;
- a customer has many permissions, basket lines and orders;
- an order has many lines;
- a category has many products;
- a product appears in many basket lines and order lines.

If decision 1 is (b), add `countries (code char(2) PK, name)`, add `cities.country_code` as a
foreign key to it, and make city names unique per country instead of globally.

Delete rules:

- **CASCADE** only where the child belongs to its parent: permissions, order lines, and the
  basket lines of a deleted customer.
- **RESTRICT** everywhere else. Deleting a customer who has orders, or a product that was sold,
  then fails instead of rewriting history.

Nothing deletes rows today; these rules only define what a delete would do.

#### 4. Business rules: domain or database

| Rule | Domain | Database |
|---|---|---|
| Email well-formed and lowercased; names not empty | ✓ | |
| Email and phone unique | | UNIQUE (only the database sees every row, including concurrent writers) |
| Phone in E.164; language and channel in their sets; quantity > 0; prices > 0 or ≥ 0 | ✓ | CHECK |
| One permission per channel; one line per product | ✓ | Primary key |
| Grant only for a reachable channel | ✓ | Not enforced (it spans two tables, and a trigger isn't worth it) |
| An order has at least one line and never changes | ✓ | Not enforced (orders are written in one transaction) |
| Referenced city, customer, product and category exist | | Foreign key |

**Rule of thumb.**

- The database enforces what it can state declaratively and what every writer must respect:
  the seeder, psql and other contexts.
- The domain enforces rules that need context or span several rows.
- Small closed sets are checked in both places. Other contexts depend on them, and the check
  costs nothing.

#### 5. Indexes and how segments will query

The schema must answer segments like these, using bind parameters only:

- **Customer attributes:** city, preferred language, signup date, and permission for the
  campaign's channel.
- **Basket activity:** added something within N days, optionally from a category or a product.
- **Purchases:**
  - ordered within N days, not within N days, or never;
  - order count or spend within N days;
  - bought from a category or a product.

Here is your example, "customers in Istanbul who added a product to their basket in the last
30 days but haven't purchased anything", for an SMS campaign:

```sql
SELECT c.id FROM customers c
WHERE c.city_id = $1                                          -- İstanbul, resolved by name
  AND EXISTS (SELECT 1 FROM basket_items b
              WHERE b.customer_id = c.id AND b.added_at >= $2) -- $2 = evaluation time − 30 days
  AND NOT EXISTS (SELECT 1 FROM orders o
                  WHERE o.customer_id = c.id AND o.ordered_at >= $2)
  AND EXISTS (SELECT 1 FROM notification_permissions p
              WHERE p.customer_id = c.id AND p.channel = $3 AND p.granted)
```

"Haven't purchased anything" can mean three things:

- never ordered;
- no order in the window;
- no order since the basket add (`o.ordered_at >= b.added_at`).

The schema supports all three; the segmentation phase must pick one. Cut-off times are
computed in Go and passed as parameters, so tests can fix "now".

Indexes beyond the primary keys (which already serve per-customer lookups of permissions and
basket lines):

| Index | Serves |
|---|---|
| customers (email) UNIQUE, (phone) UNIQUE | Uniqueness; finding a customer by address for opt-outs later |
| customers (city_id) | City filters; foreign key |
| orders (customer_id, ordered_at) | Ordered or not within N days, last order date, spend per customer; foreign key |
| basket_items (product_id) | Product and category filters; foreign key |
| order_items (product_id) | "Bought product or category X"; foreign key |
| products (category_id) | Category filters; foreign key |

Deliberately not indexed:

- names, which are never filtered on;
- `preferred_language`, which has two values, so the planner would ignore the index;
- `granted`, a boolean;
- `created_at`, until a signup-date segment needs one and EXPLAIN confirms it.

At a few thousand customers, PostgreSQL scans most tables sequentially anyway. These indexes
serve the joins above and keep them fast at 100× the data. EXPLAIN on real segment queries
will confirm them in the segmentation phase.

#### 6. Transactions and consistency

- **One aggregate per transaction:** a customer with its permissions, an order with its lines,
  or a single basket line.
- **No transaction spans the two contexts.** Foreign keys check references between them.
- **Checkout is the only cross-aggregate write**, turning a basket into an order, and it doesn't
  exist here. If it is ever added, one local transaction is fine.
- **Segment results are a snapshot.** The delivery phase must check permission again just
  before sending, because a customer can opt out in between.

Notes for the seeding phase:

- **Consistent timelines.** Signup comes before any activity, and nothing is in the future. A
  product a customer ordered after adding it is no longer in the basket, because checkout
  would have cleared it.
- **Recent activity.** Activity is generated relative to the seeding time, so "last 30 days"
  segments have members. A fixed random seed makes demos reproducible.
- **Varied behaviour.** Permission rates vary, order frequency has a long tail, and some open
  baskets are abandoned.

#### 8. Answers to your questions

1. **A separate Basket entity?**
   - No. With one open basket per customer, `basket_items` keyed by (customer, product) is
     enough.
   - The domain keeps a `Basket` type to hold the invariants.
   - A `baskets` table pays off only for several baskets per customer or basket history.
2. **Should basket lines have `added_at` and `updated_at`?**
   - `added_at`, yes: it is the abandonment signal.
   - `updated_at`, no: nothing changes a line after it is written. Add it with the first
     use case that changes quantities.
3. **Order and OrderItem separate?**
   - As tables, yes. Segments filter on the products and categories inside orders, which needs
     foreign keys and indexes; a JSONB column would lose both.
   - In the model they are one aggregate: lines are created with their order and never
     referenced alone.
4. **Product price history?**
   - No. `order_items.unit_price_minor` records what was paid, which is all that spend
     segments need.
   - History only pays off for price-drop campaigns.
5. **Permissions stored separately?** Yes, in a separate table but inside the Customer aggregate.
   - Why a separate table:
     - The channel becomes a bind parameter rather than a dynamic column name, in line with
       CLAUDE.md's rule against interpolating anything into SQL.
     - Each channel keeps its own timestamp.
     - A new channel is one more CHECK value.
   - Why the same aggregate:
     - Invariant 2 spans contact points and permissions.
     - Permissions live and die with their customer.
6. **Language preferences?**
   - One `preferred_language` per customer: an ISO 639-1 code from a closed set, as a Go type
     with a matching CHECK.
   - Not a lookup table: a new language needs content-generation support, which is a code
     change anyway.
   - Not a ranked list: one preference is enough to pick a content variant. Falling back to a
     campaign's default language belongs to the campaign phase.
7. **Indexes?** See section 5.
8. **Domain or database?** See section 4.

#### 9. Trade-offs and alternatives

- **Permissions as their own aggregate.**
  - Gain: an opt-out becomes a single upsert, with no contention against profile edits.
  - Cost: invariant 2 would need a check across aggregates.
  - Only matters at volumes this system won't see.
- **A `baskets` table with a status, or a basket event log.**
  - Gain: several baskets per customer, or history such as a basket abandoned and later
    recovered. An event log is also the most faithful "added to cart" signal.
  - Cost: both add seeder and query complexity for segments nobody needs yet.
- **A precomputed customer profile**, i.e. a materialized view with last order, order count,
  spend and basket age.
  - Gain: one-table filters, and a flat field list for the LLM.
  - Cost: it goes stale between refreshes, and its time windows are fixed. EXISTS subqueries
    handle any window, and the data is small.
- **UUIDv7 keys.** PostgreSQL 18 has a built-in `uuidv7()`.
  - Gain: the domain can assign IDs before saving, and IDs are not guessable.
  - Cost: 16-byte keys, and IDs that are harder to read in logs and the UI.
- **Money as `numeric(12,2)`.**
  - Gain: readable in SQL.
  - Cost: Go needs a decimal type. int64 kuruş is exact and simple.
- **GORM tags on the domain types**, so they double as row structs.
  - Gain: no mapping code.
  - Cost: GORM's tags and conventions move into the domain, against CLAUDE.md.
- **No foreign keys between contexts.**
  - Gain: the cleanest separation, ready for separate databases.
  - Cost: no referential integrity within the one database we actually have.

2. **Phone.**

3. **Order status.**

   - (b) `completed` or `cancelled`. More realistic, but every purchase segment must then

4. **Primary keys.**

#### 4. Business rules: domain or database

| Rule | Domain | Database |
|---|---|---|
| Email well-formed and lowercased; names not empty | ✓ | |
| Email and phone unique | | UNIQUE (only the database sees every row, including concurrent writers) |

- The database enforces what it can state declaratively and what every writer must respect.
- The domain enforces rules that need context or span rows.
- Small closed sets are checked in both places.

#### 5. Indexes and how segments will query

The schema must support these segments, using bind parameters only:

- **Customer attributes:** country, city, language, signup date, and permission for the
  campaign's channel.
- **Basket activity:** added something within N days, optionally from a category or a product.
- **Purchase history** (completed orders only):
  - ordered within N days, not within N days, or never;
  - number of orders or spend within N days;
  - bought from a category or a product.

**Example:** "customers in Istanbul who added a product to their basket in the last 30 days
but haven't purchased anything", for an SMS campaign:

```sql
SELECT c.id FROM customers c
WHERE c.city_id = $1                                          -- İstanbul, resolved by name
  AND EXISTS (SELECT 1 FROM basket_items b
              WHERE b.customer_id = c.id AND b.added_at >= $2) -- $2 = evaluation time − 30 days
  AND NOT EXISTS (SELECT 1 FROM orders o
                  WHERE o.customer_id = c.id AND o.status = 'completed'
                    AND o.ordered_at >= $2)
  AND EXISTS (SELECT 1 FROM notification_permissions p
              WHERE p.customer_id = c.id AND p.channel = $3 AND p.granted)
```

A country filter is `c.city_id IN (SELECT id FROM cities WHERE country_code = $1)`.

"Haven't purchased anything" can mean any of these, and the segmentation phase must pick one:

- never ordered;
- no order within the window;
- no order since the basket add.

The schema supports all three. It goes to DECISIONS.md as an open question.

Indexes beyond the primary keys (which already serve per-customer lookups):

| Index | Serves |
|---|---|
| cities (country_code, name) UNIQUE | Country filters (leading column); resolving a city name within a country |
| customers (email) UNIQUE, (phone) UNIQUE | Uniqueness; opt-out lookups by address later |
| customers (city_id) | City and country filters; foreign key |
| orders (customer_id, ordered_at) | Ordered or not within N days, last order date, spend; foreign key |
| basket_items (product_id) | Product and category filters; foreign key |
| order_items (product_id) | "Bought product or category X"; foreign key |
| products (category_id) | Category filters; foreign key |

Not indexed:

- names;
- `preferred_language` (three values);
- `granted` and `status` (few values, filtered per customer row);
- `created_at` (until a signup-date segment shows a need in EXPLAIN).

At a few thousand customers PostgreSQL scans most tables anyway. These indexes keep the joins
above fast at 100× the data. EXPLAIN confirms them once seed data exists.

#### 6. Transactions and consistency

- **One aggregate per transaction:**
  - a customer with its permissions;
  - an order with its lines;
  - a single order's status change;
  - one basket line.
- **No transaction spans the two contexts.** Foreign keys check references between them.
  Checkout (basket to order) would be the only write spanning aggregates, and it doesn't exist
  here.
- **Delivery re-checks permission.** A segment is evaluated at one moment, so the delivery
  phase must check permission again just before sending.

For the seeding phase:

- Timelines must be consistent: signup comes before activity, and status changes come after
  their order. Nothing is in the future.
- Products a customer ordered after adding them are no longer in their basket.
- Activity is relative to seeding time, and a fixed random seed makes runs reproducible.
- Languages follow countries, with a realistic mix (e.g. Turkish speakers in Germany).
- Some orders are cancelled or refunded, and some baskets are abandoned.

#### 8. Answers to your questions

1. **Separate Basket entity?** No. `basket_items` keyed by (customer, product) is enough for
   one open basket per customer, and the `Basket` type holds the invariants.
2. **`added_at` and `updated_at` on basket lines?** `added_at` yes: it is the abandonment
   signal. `updated_at` no: nothing changes a line after it is written.
3. **Order and OrderItem separate?**
   - As tables, yes: segments filter on the products and categories inside orders, which needs
     foreign keys and indexes.
   - In the model, they are one aggregate: lines live and die with their order.
4. **Price history?** No. `order_items.unit_price_minor` records what was paid. Price history
   goes on the further-improvements list.
5. **Permissions stored separately?** In their own table, inside the Customer aggregate.
   - A table makes the channel a bind parameter rather than a dynamic column name.
   - The aggregate keeps invariant 2 in one place.
6. **Language?** One `preferred_language` code per customer, from a closed set: a Go type plus
   a CHECK constraint.
   - Not a lookup table: a new language needs content-generation support anyway.
   - Not a ranked list: content fallback is a campaign concern.

#### 9. Trade-offs and alternatives

- **Permissions as their own aggregate.** An opt-out becomes a single upsert, but invariant 2
  would then need a check across aggregates.
- **A `baskets` table or a basket event log.** These are needed for several baskets per
  customer or for basket history. They add seeder and query complexity for segments nobody
  needs yet.
- **A precomputed segmentation profile** (a materialized view). It would turn segments into
  one-table filters and give the LLM a flat field list. But it goes stale between refreshes and
  fixes the time windows.
- **GORM tags on domain types.** These would remove the mapping code but break CLAUDE.md's rule
  of keeping GORM out of the domain.
- **No foreign keys between contexts.** This is the cleanest separation, but it gives up
  integrity in what is one database.

- a product appears in many basket lines and order lines.

Delete rules:

- CASCADE only where the child belongs to its parent: permissions, order lines, and the basket
  lines of a deleted customer.
- RESTRICT everywhere else, so deleting a customer who has orders, or a product that was sold,
  fails instead of rewriting history.

## 4. Business rules: domain or database

| Rule | Domain | Database |
|---|---|---|
| Email well-formed and lowercased; names not empty | ✓ | |
| Email and phone unique | | UNIQUE (only the database sees every row, including concurrent writers) |
| Phone in E.164; language, channel and status in their sets; quantity > 0; prices > 0 or ≥ 0; status change not before the order | ✓ | CHECK |
| One permission per channel; one line per product | ✓ | Primary key |
| Grant only for a reachable channel | ✓ | Not enforced (spans two tables; a trigger isn't worth it) |
| Order has at least one line; lines never change; only completed orders change status; end states are final | ✓ | Not enforced (needs the previous state, or is a property of one write) |
| Referenced country, city, customer, product and category exist | | Foreign key |

Rules of thumb:

- The database enforces what it can state declaratively and what every writer must respect.
- The domain enforces rules that need context or span rows.
- Small closed sets are checked in both places.

## 5. Indexes and how segments will query

The schema must support these segments, using bind parameters only:

- **Customer attributes:** country, city, language, signup date, and permission for the
  campaign's channel.
- **Basket activity:** added something within N days, optionally from a category or a product.
- **Purchase history** (completed orders only):
  - ordered within N days, not within N days, or never;
  - number of orders or spend within N days;
  - bought from a category or a product.

**Example:** "customers in Istanbul who added a product to their basket in the last 30 days
but haven't purchased anything", for an SMS campaign:

```sql
SELECT c.id FROM customers c
WHERE c.city_id = $1                                          -- İstanbul, resolved by name
  AND EXISTS (SELECT 1 FROM basket_items b
              WHERE b.customer_id = c.id AND b.added_at >= $2) -- $2 = evaluation time − 30 days
  AND NOT EXISTS (SELECT 1 FROM orders o
                  WHERE o.customer_id = c.id AND o.status = 'completed'
                    AND o.ordered_at >= $2)
  AND EXISTS (SELECT 1 FROM notification_permissions p
              WHERE p.customer_id = c.id AND p.channel = $3 AND p.granted)
```

A country filter is `c.city_id IN (SELECT id FROM cities WHERE country_code = $1)`.

"Haven't purchased anything" can mean any of these, and the segmentation phase must pick one:

- never ordered;
- no order within the window;
- no order since the basket add.

The schema supports all three. It goes to DECISIONS.md as an open question.

Indexes beyond the primary keys (which already serve per-customer lookups):

| Index | Serves |
|---|---|
| cities (country_code, name) UNIQUE | Country filters (leading column); resolving a city name within a country |
| customers (email) UNIQUE, (phone) UNIQUE | Uniqueness; opt-out lookups by address later |
| customers (city_id) | City and country filters; foreign key |
| orders (customer_id, ordered_at) | Ordered or not within N days, last order date, spend; foreign key |
| basket_items (product_id) | Product and category filters; foreign key |
| order_items (product_id) | "Bought product or category X"; foreign key |
| products (category_id) | Category filters; foreign key |

Not indexed:

- names;
- `preferred_language` (three values);
- `granted` and `status` (few values, filtered per customer row);
- `created_at` (until a signup-date segment shows a need in EXPLAIN).

At a few thousand customers PostgreSQL scans most tables anyway. These indexes keep the joins
above fast at 100× the data. EXPLAIN confirms them once seed data exists.

## 6. Transactions and consistency

- **One aggregate per transaction:**
  - a customer with its permissions;
  - an order with its lines;
  - a single order's status change;
  - one basket line.
- **No transaction spans the two contexts.** Foreign keys check references between them.
  Checkout (basket to order) would be the only write spanning aggregates, and it doesn't exist
  here.
- **Delivery re-checks permission.** A segment is evaluated at one moment, so the delivery
  phase must check permission again just before sending.

For the seeding phase:

- Timelines must be consistent: signup comes before activity, and status changes come after
  their order. Nothing is in the future.
- Products a customer ordered after adding them are no longer in their basket.
- Activity is relative to seeding time, and a fixed random seed makes runs reproducible.
- Languages follow countries, with a realistic mix (e.g. Turkish speakers in Germany).
- Some orders are cancelled or refunded, and some baskets are abandoned.

## 8. Answers to your questions

1. **Separate Basket entity?** No. `basket_items` keyed by (customer, product) is enough for
   one open basket per customer, and the `Basket` type holds the invariants.
2. **`added_at` and `updated_at` on basket lines?** `added_at` yes: it is the abandonment
   signal. `updated_at` no: nothing changes a line after it is written.
3. **Order and OrderItem separate?**
   - As tables, yes: segments filter on the products and categories inside orders, which needs
     foreign keys and indexes.
   - In the model, they are one aggregate: lines live and die with their order.
4. **Price history?** No. `order_items.unit_price_minor` records what was paid. Price history
   goes on the further-improvements list.
5. **Permissions stored separately?** In their own table, inside the Customer aggregate.
   - A table makes the channel a bind parameter rather than a dynamic column name.
   - The aggregate keeps invariant 2 in one place.
6. **Language?** One `preferred_language` code per customer, from a closed set: a Go type plus
   a CHECK constraint.
   - Not a lookup table: a new language needs content-generation support anyway.
   - Not a ranked list: content fallback is a campaign concern.
7. **Indexes:** section 5.
8. **Domain or database:** section 4.

## 9. Trade-offs and alternatives

- **Permissions as their own aggregate.** An opt-out becomes a single upsert, but invariant 2
  would then need a check across aggregates.
- **A `baskets` table or a basket event log.** These are needed for several baskets per
  customer or for basket history. They add seeder and query complexity for segments nobody
  needs yet.
- **A precomputed segmentation profile** (a materialized view). It would turn segments into
  one-table filters and give the LLM a flat field list. But it goes stale between refreshes and
  fixes the time windows.
- **GORM tags on domain types.** These would remove the mapping code but break CLAUDE.md's rule
  of keeping GORM out of the domain.
- **No foreign keys between contexts.** This is the cleanest separation, but it gives up
  integrity in what is one database.
