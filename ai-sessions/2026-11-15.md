#### What's built
- **Assistant** (`internal/assistant`): chat with Claude through the standard Messages API, with native tool calls. The default model is `claude-haiku-5-5`, changeable with `ANTHROPIC_MODEL`, with no thinking, caching or beta features.
  - **Tools:** six, and Go checks every call before anything runs. It rejects unknown tools and unknown fields, and the existing campaign and segmentation services apply their rules.
  - **Privacy:** the model sees campaign settings, message templates and counts, never customers.
  - **Conversations** live in memory: 2 hours after the last message, at most 500.
- **Approval-gated dispatch:** asking to send a campaign only shows an approval card in the chat. Each approval works once, and a repeat gets 409.
  - Approving sends only the version you approved. That check happens in the same database transaction as the dispatch, so the race in the first plan is gone.
  - Nothing in the chat can approve, including typing "yes, send it".
- **Mock mode** (`LLM_PROVIDER=mock`) is the default. It plays a fixed script, whatever you write: create a demo draft, estimate it, ask to send it.
- **Chat page** (`/assistant`): message bubbles, and cards for drafts, estimates and approvals. Drafts link to the existing editor, and the conversation survives a trip to the editor and back.
- **Configuration:** `LLM_PROVIDER`, `ANTHROPIC_API_KEY` (never logged) and `ANTHROPIC_MODEL`, read from `.env`, with placeholders in `.env.example`.

I found real problems in all three areas. Below are the problems, each with a concrete failure, and then the plan. I haven't changed any code.

#### Problems

##### 1. Eviction can remove a conversation while it is answering
- [store.go:48-66](internal/assistant/store.go#L48-L66): `open` returns the conversation pointer after it releases the store's lock. The turn's lock (`conv.mu`) is taken later, in `Chat`, and the store never sees it. `evict` and `oldest` choose by `lastUsed` alone, so they can't tell a conversation that is answering from an idle one.
- **Capacity eviction, a concrete case:**
  1. A turn starts. `lastUsed` was set when its message arrived.
  2. The turn can run for up to 90 s. If 500 other conversations are opened or used in that time (a burst, or a script against this unauthenticated endpoint), it becomes the oldest and is dropped.
  3. The turn carries on with the orphaned pointer. Its tools still create drafts, and it answers 200 with a `conversation_id` that no longer exists. The next message gets 404.
  4. `drop` also deletes the approvals behind earlier cards, so clicking Approve on them gets 404.
  5. An approval the turn records after the drop belongs to a conversation that no longer exists, yet stays approvable for 2 h.
- **TTL eviction** can't hit a turn in progress today, but only because 90 s is much shorter than 2 h. Nothing enforces it.
- **`lastUsed`** is set when a message arrives, so:
  - a message refused as busy or full still keeps the conversation alive;
  - the TTL counts from the start of the last turn, not its end.

##### 2. Rolling back a failed turn hides work that was really done
- [assistant.go:176-179](internal/assistant/assistant.go#L176-L179): any model error truncates the history and returns only the error, even after tools have changed the database. A concrete case:
  1. "Create a spring sale campaign" → `create_campaign` creates draft #42.
  2. The next model call fails (529 or timeout).
  3. The history is rolled back and the card is thrown away. The UI shows an error and puts the text back in the input.
  4. The user sends it again, and the model, which doesn't know about #42, creates a second draft. Later requests like "rename it" can't find #42 either.

  A dispatch request in that turn leaves an approval whose card never reached the user.
- **Timeouts and disconnects take the same path:** `classify` turns a cancelled context into `assistant_timeout`, which is also rolled back.
- **When the rollback is still right:** when nothing changed, meaning the first model call failed or only reads ran (get, list, estimate).
- **Keeping the turn is safe for the history:** it would end with tool results, followed by the next user message. The API merges consecutive user messages, and the `step_limit` path already depends on that today.

##### 3. Model and tool call limits
- **The 5th model call** ([assistant.go:170-173](internal/assistant/assistant.go#L170-L173)): if it asks for tools, they run and change data. Then the loop stops with `step_limit`, so the model never sees their results in that turn. If one of them fails (for example an invalid update), the user sees nothing about it: no card and no reply.
- **The `step_limit` text** says "Try a simpler request", even though the work shown was done and the conversation can simply continue.
- **After the 10-tool budget is spent** ([assistant.go:191-196](internal/assistant/assistant.go#L191-L196)), the loop keeps calling the model. Every tool call it asks for is refused, so up to 4 more paid calls can achieve nothing.
- **Completed operations** keep their cards when the step limit is hit. But combined with problem 2, a model failure on calls 2–5 loses them all.

#### Plan

**1. Store** ([store.go](internal/assistant/store.go), [assistant.go](internal/assistant/assistant.go))
- **One lock instead of two.** Replace `conversation.mu` with a `busy` flag guarded by the store's existing mutex.
  - `open` checks and sets it in one step; a busy conversation still gets `ErrConversationBusy`.
  - A new `release(c, now)` clears it and sets `lastUsed`. `Chat` calls it in a deferred closure, so it reads the time at the end of the turn.
- **Eviction skips busy conversations.** `evict` and `oldest` skip conversations marked busy.
- **When all 500 are busy,** a new conversation is refused with `ErrTooManyConversations`. The API answers 503 `assistant_busy`, an existing code whose UI text already exists. This keeps the 500 limit hard, and it also prevents a nil dereference in `oldest`.
- **`lastUsed` changes only when a turn ends,** so the TTL runs from the last answer.

**2. Keep turns that changed something** ([assistant.go](internal/assistant/assistant.go))
- **Track changes.** Note whether a tool changed something in this turn: a campaign created or updated, or a dispatch request recorded.
- **On a model error, timeout or cancellation:**
  - if nothing changed, roll back and return the error, as today;
  - otherwise keep the history up to the last tool results, count the turn, log the error, and return 200 with the cards and a new notice, `interrupted`.
- **Frontend:** add `'interrupted'` to the notice type, choose the text per notice, and add the en/tr texts.

**3. Limits** ([assistant.go](internal/assistant/assistant.go))
- **The reply that reaches a limit runs no tools.** This is the 5th model call, or the first call after the tool budget is spent. Its tool calls are answered `too_many_tool_calls`, which keeps the history valid, and the turn ends with `step_limit`.
  - Every tool that runs now has its result seen by the model within the turn.
  - At most one model call is made after the budget is spent, instead of up to 4.
- **The `step_limit` text becomes:** "…What it finished is shown above; send another message to continue."

**4. Tests** (with `-race`, no database)
- **Store:**
  - busy conversations survive TTL and capacity eviction;
  - the TTL counts from the end of the turn;
  - a full store of busy conversations is refused.
- **Concurrency:**

func (m *scripted) reply(_ context.Context, _ string, history []message) (message, error) {
	m.mu.Lock()
	m.seen = append(m.seen, slices.Clone(history))
	if len(m.replies) == 0 {

	next := m.replies[0]
	m.replies = m.replies[1:]
